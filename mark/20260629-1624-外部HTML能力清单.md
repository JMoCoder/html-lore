# 外部 HTML 生成能力清单

日期：2026-06-29

## 背景

本文件对应 AI 生成样式优化讨论中的第三部分：建立外部能力清单文档。

当前项目已经实现 AI 生成 v2 的默认 skill 路由和三类可选增强 skill。下一阶段需要继续评估外部成熟项目，但当前先不 vendor、不作为依赖引入、不复制外部 prompt / template / code，只做能力、许可和接入方式的前置记录。

本阶段原则：

- 默认链路仍由项目内 LangGraph 多 Agent 工作流负责。
- 默认 skill 是通用底座，可选增强 skill 是辅助，不替代默认 skill。
- 外部项目先按能力拆解，不按项目名硬接入。
- 所有外部项目正式接入前必须再做 license、依赖、安全、产物权属和部署体积审查。

## 能力拆解

### 1. Presentation / Deck

对应外部能力：

- pakco-html 的 deck / full deck / presenter mode / style picker。
- html-anything 的 keynote deck、poster、frame、social surface。
- effective-html 的 plan page。

可借鉴点：

- 把“用户说不清楚风格”转为可选视觉菜单。
- deck / presentation 类型需要更强的节奏：封面、问题、机会、方案、能力、路线图、证明、行动。
- 生成侧不应只要求“高级感”，而应给 StyleDesigner 结构化的视觉目标和版式约束。

当前适合落地为：

- 本地增强 skill：`presentation_surface_design` 已有，可继续完善。
- 前端可选风格入口：第二阶段再讨论是否做 visual taste picker。
- 外部模板：暂不接入，先不引入模板资产。

风险点：

- pakco-html 聚合多个上游项目，不能只看 pakco 自身 MIT；必须逐一确认上游素材、模板和 prompt 的许可。
- deck 模板很容易造成产物同质化，应作为参考能力，不应覆盖模型默认自主设计。

### 2. Architecture / System Map

对应外部能力：

- effective-html 的 `html-diagram`。
- html-anything 中工程、runbook、prototype、data report 类 skill。

可借鉴点：

- 系统图、架构图、状态机、runtime loop 应优先使用 SVG / HTML 原生布局表达，不依赖外部 JS。
- 图表说明要避免标题、箭头、loop 标签和节点重叠。
- 架构解释页需要把节点、edge、条件路由、回退逻辑、状态所有权讲清楚。

当前适合落地为：

- 本地增强 skill：`architecture_explainer_design` 已有，可继续完善。
- 后续工具：可考虑受控 SVG layout helper，但当前不做。

风险点：

- effective-html README 提到每个 skill 包含 `html-effectiveness` 示例语料；示例语料来源和可再分发边界需要单独确认。
- 如果直接复制其示例或 prompt，容易带来版权和风格同质化问题。

### 3. Component Patterns / Dense Report

对应外部能力：

- pakco-html 的 skins、single-page layouts、CSS animations、canvas FX。
- html-anything 的 data report、office、prototype、dashboard 类 surface。

可借鉴点：

- 内容密集页需要稳定组件：指标、时间线、对比表、风险矩阵、流程、引用、结论框。
- 组件应由信息结构驱动，不应为了“炫”而堆卡片。
- 表格、流程、左右分栏、摘要区等需要明确响应式降级。

当前适合落地为：

- 本地增强 skill：`component_pattern_html` 已有，可继续完善。
- 后续工具：可考虑受控 component pattern helper，输出结构化 layout hints，而不是输出完整 HTML 模板。

风险点：

- 动画和 canvas FX 容易增加安全和性能风险。
- 过度模板化会降低大模型自主设计能力。

### 4. Live Preview / Workflow Detail / Export

对应外部能力：

- html-anything 的 SSE streaming render、iframe preview、HTML/PNG/export。

可借鉴点：

- 当前项目工作流详情页已经有 SSE / polling 基础，可以继续向“实时生成过程可视化”靠拢。
- 预览层应 sandbox，生成物仍需经过 SafetyReviewer 和 HTML safety scan。
- 导出链路可作为第二阶段或第三阶段能力，不进入当前样式质量优化主线。

当前适合落地为：

- 工作流详情页增强。
- 后续预览/导出设计参考。

风险点：

- html-anything 是完整 Next / pnpm workspace，直接依赖会显著增加部署复杂度。
- 它通过本地 coding-agent CLI 执行生成；这与当前服务端 provider API 模式不同，不适合直接嵌入当前 runtime。

## 接入方式候选

### A. 只做能力摘要和本地 skill

含义：

- 阅读外部项目，提炼通用原则。
- 用项目内部原创文字写入 `generation_v2/skills/`。
- 不复制外部代码、模板、示例、图片或 prompt。

优点：

- 许可风险最低。
- 不增加运行依赖。
- 与当前 Skill Router 最匹配。

缺点：

- 提升依赖我们自己的总结质量。
- 不能直接使用外部项目已有 preview/template 资产。

当前建议：短期采用。

### B. 外部项目作为可选依赖

含义：

- 将外部项目作为 npm/python/git 依赖或独立安装项。
- Runtime 通过 tool adapter 受控调用。

优点：

- 能复用成熟预览、模板、导出能力。
- 项目升级可跟随上游。

缺点：

- 部署体积、依赖风险、license 审查、sandbox 权限都会复杂化。
- Agent 不能直接面对外部项目，必须经过 tool adapter。

当前建议：后续单独决策，不进入当前版本。

### C. Vendor 子目录或 submodule

含义：

- 把外部项目源码带入仓库或以 submodule 固定版本。

优点：

- 可控、可审计、可固定版本。

缺点：

- 许可、更新、安全、体积和维护成本最高。
- 容易把外部模板和素材权属问题带进仓库。

当前建议：暂不采用。

### D. 外部模板 / 示例仅作参考索引

含义：

- 只记录外部项目、license、能力标签、示例 URL。
- 运行时不读取、不复制、不分发。

优点：

- 可作为人工选型和后续讨论资料。
- 风险低。

缺点：

- 不能自动提升生成质量。

当前建议：可以与 A 并行。

## License 与合规检查清单

外部 skill pack 入库方案已暂停。不能只把外部 skill 总结/改写后作为“外部调用”接入；如果后续真正引入第三方能力，需要重新经过 Decision Gate，明确是完整 vendor、依赖/submodule、runtime tool adapter，还是仅作为内部原创 skill 的参考来源。

正式接入任何外部项目之前，需要逐项确认：

- 仓库 LICENSE 文件是否存在、是否与 README 一致。
- 是否包含上游项目、第三方模板、图片、字体、图标、示例语料。
- 上游项目 license 是否允许商业使用、修改、再分发。
- 是否要求保留 NOTICE、copyright、license 文本。
- 是否含有品牌、商标、专有素材或不可再分发截图。
- 是否需要在生成产物中保留署名。
- 是否会把外部代码、prompt、模板直接写入本项目仓库。
- 是否会在运行时读取用户文件、环境变量、shell、网络或本地 agent CLI。
- 是否会引入 CDN、外链脚本、远程字体、iframe、canvas、WebGL 或导出依赖。
- 是否会改变当前“默认自主设计、skill/tools 增强”的架构原则。

## 当前结论

1. 三个项目都有可借鉴价值，但现在不适合整体集成。
2. 当前最稳妥路线是继续用内部原创 skill 承接外部项目的通用经验。
3. `effective-html` 更适合架构图、计划页和系统说明能力参考。
4. `pakco-html` 更适合视觉菜单、deck 风格选择和 presentation 能力参考，但上游许可需要重点审查。
5. `html-anything` 更适合产品架构、skill catalog、实时预览、导出链路参考，不适合作为当前服务端生成链路的直接依赖。
6. 后续真正接入方式需要单独 Decision Gate：依赖、vendor、submodule、metadata-only、runtime tool adapter 只能择一或分层组合，不能临时混用。

## 外部工具 / 依赖候选分析

> 本节是分析，不是接入决策。当前不新增依赖、不 vendor 外部项目、不改变运行链路。

本轮进一步检查三个成熟项目后，结论是：

- `effective-html` 更像 skill / prompt / example corpus，没有明显需要引入的运行时工具依赖。
- `pakco-html` 更像视觉菜单和模板包装层，没有 package 级运行时依赖；它的核心价值是“style picker / prompt picker / preview catalog”。
- `html-anything` 是完整 Next 应用，依赖中存在若干可拆解的工具能力，但不适合整体引入。

### 第一优先级候选：浏览器渲染验收

如果目标是显著提升“样式可交付性”，最值得优先分析的是浏览器渲染验收，而不是模板库。

原因：

- 当前问题集中在视觉破版：右侧空白、标题重叠、底层线条透出、组件不匹配。
- 这些问题靠 LLM 自评不稳定，但可以用浏览器真实渲染捕捉。
- 项目已经有 Playwright e2e 和系统 Chrome 通道经验，新增运行时能力的认知成本较低。

可能实现方向：

- 作为 `Verifier` 之后、`SafetyReviewer` 之前的可选 visual check tool。
- 输入为 HTMLDraft。
- 在临时 sandbox 中用系统 Chrome 打开。
- 输出结构化 `VisualCheckReport`：
  - 是否空白。
  - 是否有横向溢出。
  - 关键标题和图形是否重叠。
  - 移动端是否破版。
  - 主要内容是否被固定工具栏遮挡。
  - 截图像素是否非空、是否过暗、是否大面积单色。
- 如果 fail，把报告交给 HTMLCoder 修订，而不是 Runtime 自己改 HTML。

关键边界：

- Runtime 只做截图和检测，不做业务审美判断。
- Agent 根据 `VisualCheckReport` 决定如何修。
- 该 tool 默认可以先只在开发/高质量模式开启，避免普通生成耗时过长。

### 第二优先级候选：结构化表格 / 数据解析

如果用户上传 Excel / CSV / JSON / SQL，HTML 样式质量很大程度取决于 Planner 和 ContentWriter 是否拿到结构化数据。

当前 MarkItDown 能把多文件转 Markdown，但对“数据报告”类页面，纯文本化可能不够：

- 表头、单位、分组、时间序列容易丢失结构。
- 图表和指标卡需要识别数值列、分类列、日期列。
- LLM 需要明确知道哪些字段可做 KPI、趋势、对比、风险矩阵。

可能工具候选：

- Python 标准库 `csv`：CSV / TSV 基础解析，低成本。
- `openpyxl`：xlsx 结构化解析，适合轻量引入。
- `pandas`：能力强但依赖重，不适合第一步默认引入。
- JS `xlsx`：html-anything 使用，但该包历史安全和维护争议较多，不建议服务端优先选。

可能实现方向：

- 不替代 MarkItDown。
- 作为 Ingest 的增强 parser 分支：专业解析 -> MarkItDown -> basic fallback。
- 输出进入 `ParsedDocument.tables` 或新增 `StructuredTable`。
- Planner 根据表格元信息决定是否触发 `data_report` / `dashboard` / `comparison_table` skill。

### 第三优先级候选：CSS 内联和截图导出

这两类工具主要提升“交付渠道”和“分享效果”，不是当前 HTML 生成质量的核心。

可保留到后续：

- `juice`：当明确要支持公众号 / 知乎 / 邮件粘贴时再引入。
- `modern-screenshot` 或 Playwright screenshot：当明确要支持社交图、封面图、PNG 导出时再引入。

当前不建议为了样式优化提前接入，因为会扩大前端和部署复杂度。

### 不建议进入当前项目的能力

短期不建议接入：

- 本地 coding-agent CLI adapter：与当前服务端 provider API、任务队列、权限边界不一致。
- 整体 Next/React/Tailwind 应用：属于前端重构决策，不是生成质量工具。
- 外部模板 runtime 直接调用：会引入版权、同质化和安全边界问题。
- canvas FX / heavy animation library：对知识库笔记价值有限，且增加性能和安全风险。

### 当前分析结论

如果继续走“内部原创 skill 承接外部通用经验”的路径，真正可能进入项目的外部工具/依赖应按以下顺序继续评估：

1. **Playwright / 系统 Chrome 渲染验收 tool**：最直接提升样式可靠性和商业化交付感。
2. **结构化表格解析 tool**：增强 Excel / CSV / 数据报告类生成质量。
3. **HTML/CSS 安全净化 tool**：作为当前自研安全扫描的增强，不作为样式主线。
4. **CSS 内联 / PNG 导出 tool**：等平台发布、分享、导出需求明确后再评估。

当前不建议接入完整外部项目，也不建议把 pakco-html / effective-html 的模板或示例语料复制进仓库。更合理的路径仍是：

外部项目经验 -> 能力标签 -> Planner `tool_needs` -> 内部原创 skill -> 必要时调用受控 tool -> Verifier / VisualCheckReport 反馈修订。

## 内部原创 Capability Map

三个成熟项目后续只作为参考资料，不进入运行时 skill pack。当前内部能力按“用户意图和页面关系”拆分，而不是按外部项目拆分：

| 能力标签 | 触发意图 | Planner 应表达 | 内部 skill 承接 | 当前重点 |
| --- | --- | --- | --- | --- |
| `presentation_surface` | 路演、汇报、PPT-like、对外分享 | 每个 section 的单一主信息、talk-track 顺序、首屏价值表达 | `presentation_surface_design` | 避免大空白卡片、面板风格不一致、虚假营销化 |
| `architecture_explainer` | 架构、工作流、agent、runtime、节点边、loop | 节点、边、边界、loop 条件、停止条件、代码/模型/用户控制边界 | `architecture_explainer_design` | 避免标题碰撞、连接线穿透文本、流程关系被卡片网格稀释 |
| `business_report` | 规划、业务分析、管理报告、发展框架 | 结论前置、风险/建议/路线、责任或参数矩阵 | `html_page_design` + `component_pattern_html` | 表格/对比/摘要块优先，避免所有内容卡片化 |
| `plan_roadmap` | 计划、实施路径、阶段、清单 | 阶段、目标、输入输出、依赖、验收点 | `html_page_design` + `component_pattern_html` | timeline/process-flow 优先，不发明日期和责任人 |
| `component_patterns` | 密集组件、表格、流程、对比、callout | 每个 section 的表现形式和验收目标 | `component_pattern_html` | 组件大小随内容密度，统一同组视觉语言 |
| `reference_style` | 用户上传样式参考 | 只提取色彩、节奏、组件形状、密度，不复制品牌/内容 | `html_page_design` | 参考样式作为证据，不压制模型自主规划 |

执行原则：

- 默认 `html_page_design` 是通用底座，始终保持模型自主规划。
- 可选增强 skill 是辅助，不替代默认 skill。
- Planner 负责判断需要哪些能力，并在 `tool_needs.reason` 中写清为什么需要。
- StyleDesigner 负责把能力转换为具体 StyleBrief 合同。
- HTMLCoder 负责执行合同，不重新发明页面策略。
- Verifier 负责按可观察问题判断是否回路修订。
