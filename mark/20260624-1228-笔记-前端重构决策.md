# 前端重构决策

## 一句话概括

HTMlore 当前前端仍采用传统 HTML/CSS/JS 静态模式，短期继续推进功能，但当 AI 生成、修改、任务历史等复杂工作台能力开始大量复用状态和组件时，必须提醒用户重新决策是否引入 React/Vue/Vite 等前端架构，而不是继续在旧结构上硬修。

## 背景

当前项目没有使用 React、Vue、Tailwind、Vite、Webpack 等现代前端框架。前端主体由以下文件承担：

- `app_static/index.html`
- `app_static/style.css`
- `app_static/app.js`
- `docs/demo/*`

这种模式部署简单、对自托管友好、静态 demo 维护成本低，但随着 AI 生成模块、任务状态页、详情页、失败重试、生成历史、HTML 修改等功能增加，单文件状态管理和全局 CSS 会越来越难维护。

## 核心内容

短期决策：

- 暂不立即引入 React/Vue/Tailwind。
- 继续在现有静态架构下完成 AI 生成前端优化。
- 新增前端代码应尽量模块化，减少全局状态和 DOM 绑定的扩散。
- 不为了局部小问题无限硬修 `app.js` 和全局 CSS。

需要提醒用户重新决策的触发点：

- AI 生成主体验收后，开始系统性建设任务状态页、详情页、失败重试、历史列表、HTML 预览或编辑入口。
- 出现第二个复杂工作台页面，例如独立任务历史页、HTML 修改页、生成结果管理页。
- 多个模块开始共享复杂状态，例如任务队列、AI 对话、生成历史、当前笔记、上传文件、用户设置、权限状态、通知中心。
- 前端修改经常需要同时改大量 DOM 查询、状态字段、渲染函数和事件绑定。
- `app.js` 继续膨胀，导致局部 UI 优化变成高风险改动。

候选路线：

- React + Vite：更适合复杂工作台、状态复用、组件生态和长期维护。
- Vue + Vite：也可作为候选，适合渐进式迁移和清晰模板结构。
- Tailwind：不作为默认立即引入项，除非决定系统性重做设计规范。

> [!tip] 关键要点
> 到达复杂工作台阶段时，应先做前端架构决策，再继续大规模堆功能。

> [!warning] 注意事项
> 不要在没有明确决策的情况下，为了短期交互问题继续把大量业务状态、任务状态和视觉逻辑硬塞进现有静态单文件结构。

## 实际应用

后续开发 AI 生成前端优化时，仍可使用当前静态架构完成小步迭代；但当需求进入独立任务历史页、生成详情页、修改模块、权限/成本策略等阶段时，Codex 需要主动提醒用户：

> 当前前端复杂度已接近重构触发点，建议先决策是否引入组件化框架，再继续开发。

该提醒必须发生在继续扩大前端复杂度之前。
