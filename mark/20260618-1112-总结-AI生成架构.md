状态控制
  -> 解析文档
  -> 分析需求

  -> 调用技能 / 参考

其中“解析文档”“调用哪些技能/参考哪些开源项目”暂不决策，后续单独讨论。

已确认的第一项架构决策：

- HTML 生成主架构采用 `LangGraph`。
- LangGraph 负责状态图、节点编排、条件路由、循环回退和运行 trace。
- LangGraph 不等于完整 Runtime。项目仍需要 Runtime / Tool / Skill / Write Gateway：
  - Runtime：承载任务执行、状态持久化、超时、重试、成本上限、日志和 API 对接。
  - Tool / Skill：受控能力层，如文档解析、搜索、样式提取、HTML 安全扫描。
  - Write Gateway：受控写入层，负责创建 HTML、写 metadata、build、审计、回滚。
  - Agent 节点：负责需求理解、规划、内容撰写、样式设计、代码生成、质量审查等智能判断。

优化后的工作流草案：

```text
Generation Runtime
  -> 初始化任务 / 读取用户输入 / 建立 GenerationState
  -> LangGraph Orchestrator
      -> Ingest / 文档解析节点
      -> Requirement Analyst / 需求分析 Agent
      -> Planner / 生成方案 Agent
      -> Content Writer / 正文内容 Agent
      -> Skill Executor / 工具与参考调用节点
      -> Style Designer / 样式设计 Agent
      -> HTML Coder / HTML 生成 Agent
      -> Verifier / 需求达成验证 Agent
      -> Safety Reviewer / 安全检查节点
      -> Final Reviewer / 主控验收 Agent
      -> Finalizer / 生成 CreateNoteProposal
  -> Write Gateway
      -> 写入资料库
      -> 默认 collection = inbox
      -> build / index / run 记录
```

验证与回退草案：

```text
Verifier 不达标
  -> 如果是内容缺失 / 逻辑不清：回到 Content Writer
  -> 如果是需求理解错误：回到 Requirement Analyst
  -> 如果是结构方案错误：回到 Planner
  -> 如果是样式不符合：回到 Style Designer
  -> 如果是 HTML 代码问题：回到 HTML Coder
  -> 如果是缺少证据 / 参考不足：回到 Skill Executor

Safety Reviewer 不通过
  -> 如果可自动修复：回到 HTML Coder / Style Designer
  -> 如果涉及高风险脚本、外链、隐私泄漏：终止或要求用户确认

Final Reviewer 不满意
  -> 根据审查报告路由到最小必要节点重跑
  -> 设置最大循环次数和成本上限，避免无限生成
```

Runtime 的职责边界：

- 允许 Runtime 判断节点是否成功、是否超时、是否达到循环上限、是否安全门禁通过。
- 不建议 Runtime 用大量业务关键词写死“该怎么回答/怎么生成”。
- 需求达成与内容质量应主要由 Agent 节点给出结构化审查报告，再由 LangGraph 条件边做路由。
- Runtime 可以执行硬规则：文件大小、HTML 安全策略、路径白名单、模型成本、失败重试、写入权限。

已确认的第二项架构约束：

- 必须吸取知识库问答环节的经验，Runtime 不参与业务判断，除非是必须且确定的少量硬规则节点。
- HTML 生成是项目核心能力，开发阶段优先保证生成质量、智能体协作链路和模块解耦，不以节省模型调用成本为第一目标。
- 允许在 Verifier / Reviewer / Planner 等环节增加必要的 LLM 调用和回退循环。
- 成本优化推迟到业务稳定之后再做，例如减少冗余审查、缓存中间结果、合并低价值节点、降低部分节点模型规格。
- 任何成本收缩都不能重新退化为 Runtime 硬编码业务判断。

已确认的第三项讨论方向：文档解析层采用多层工具链，而不是完全自研。

- 第一阶段输入类型：HTML、Markdown、TXT、PDF、Word、PPT。
- 第二阶段输入类型 / 降级场景：Excel、通过链接生成、复杂网页抓取、扫描件 PDF、图片型文档、复杂 PPT 动画或版式。
- Excel 暂放第二阶段，不进入第一版核心链路。
- 通过链接生成也暂放第二阶段，因为它涉及网页抓取、反爬、动态渲染、正文抽取、站点安全和来源可信度，复杂度接近一个独立 ingest 子系统。
- 文档解析不应完全自研。更合理的方式是多层解析链：

```text
专用解析器 / 专用工具
  -> MarkItDown
  -> 本地轻量解析
  -> 失败并返回 warning
```

暂定原则：

- 对确定性强、质量要求高的格式，优先用专用解析器或专用工具。
- MarkItDown 作为通用兜底层是必要的，适合把多种文件转成 LLM 友好的 Markdown。
- 本地轻量解析只作为最后兜底，例如 HTML/MD/TXT 的基础文本提取，不能假装能高质量理解复杂 Office/PDF。
- 第一阶段不设计“要求用户补充材料”的新交互环节；解析不足只进入 warnings，供后续 Agent 判断如何保守生成。
- Parser 只负责提取内容、结构和样式线索，不负责需求判断和最终生成策略。
- Runtime 可以判断文件大小、格式、解析是否失败、是否需要降级；不能用业务关键词决定“该生成什么”。
- 解析工具必须在受控输入路径、大小限制、URI/网络限制下运行，不能让第三方解析器拥有任意文件或网络访问能力。

MarkItDown 当前定位与注意事项：

- Microsoft MarkItDown 是将多种文件和 Office 文档转换为 Markdown 的 Python 工具，面向 LLM 和文本分析管线。
- 官方支持范围包括 PDF、PowerPoint、Word、Excel、HTML、文本类格式、ZIP、YouTube URL 等。
- 官方同时提醒它会以当前进程权限执行 I/O，因此服务端使用时必须限制输入、路径、URI scheme、网络目标等。
- 这进一步说明解析层要进入 Tool/Skill + Runtime 安全边界，而不是让 Agent 或 Web 主进程随意调用。

已确认的第四项产品/状态要求：AI 生成必须是异步任务，并提供可观测状态。

- 用户提交文件和需求后，理论上已经进入异步生成阶段，用户可以离开当前页面继续做其他事情。
- 前端需要有状态页或队列入口，用于查看任务队列、生成历史和每个任务的当前阶段。
- 这不是生成智能体主链路本身，但开发时必须提前考虑任务状态模型，避免后续只能显示“排队中/完成”。
- 状态应能映射 LangGraph / Runtime 的主要阶段，例如：

```text
queued / 等候中
parsing / 解析中
parse_failed / 解析失败
analyzing_requirements / 分析需求中
planning / 规划中
writing_content / 撰写内容中
executing_skills / 调用技能中
designing_style / 设计样式中
coding_html / 生成 HTML 中
verifying / 验证中
safety_checking / 安全检查中
finalizing / 收尾中
writing / 写入资料库中
completed / 已完成
failed / 失败
canceled / 已取消
```

- 每个阶段应尽量记录：阶段名、开始时间、结束时间、简短说明、是否可重试、错误摘要。
- 任务完成后进入生成历史；失败任务保留错误摘要和重试入口。
- 这个状态系统应复用现有 AI 任务队列 / 生成历史基础，但状态粒度要为新多 Agent 生成链路预留。
- 加分项记录：状态页除了任务列表外，后续可以支持点击任务详情，查看 AI 处理过程 / 阶段回放 / Agent 正在做什么，类似对话中可见的“正在分析、正在检索、正在生成”。页面视觉仍保持项目统一风格，不追求花哨页面；当前只记录需求，暂不展开具体规划。

已进入的下一轮讨论方向：Agent 分工与中间产物 schema。

建议不要把 Agent 拆得过细，第一版以“少而清晰”为原则，优先保证每个节点职责单一、输出稳定、能回退。

推荐的第一版分工：

```text
Ingest / Parser / 文档接入与解析器
  -> 解析文件、提取结构、图片、链接、样式线索、warnings

Requirement Analyst / 需求分析智能体
  -> 解释用户需求、目标用途、受众、约束、成功标准

Planner / 方案规划智能体
  -> 生成生成方案、页面结构、模块顺序、写作策略、风险点

Content Writer / 内容写作智能体
  -> 产出正文内容、段落草案、标题层级、信息组织

Style Designer / 样式设计智能体
  -> 产出视觉风格、色彩、排版倾向、组件风格、参考映射

HTML Coder / HTML 编码智能体
  -> 把内容 + 样式方案编成具体 HTML / CSS / 轻量 JS

Skill Executor / 技能与工具执行器
  -> 调用搜索、外部参考、MarkItDown、专用解析器等工具

Verifier / 需求达成验证智能体
  -> 检查是否满足需求、是否缺内容、是否偏题、是否结构失衡

Safety Reviewer / 安全审查智能体
  -> 检查安全性、外链、脚本、隐私、公共分享风险

Finalizer / 交付封装器
  -> 组装 CreateNoteProposal，交给 Write Gateway
```

```text

  - source_files

PlanDraft / 方案草案
  - page_goal

  - content_strategy
  - tool_needs
  - risks

ContentDraft / 内容草稿
  - title
  - summary
  - sections

StyleBrief / 样式简报
  - layout
  - colors
  - typography

  - html

  - ok

  - ok

  - title

```

建议的设计原则：

- Agent 的输出必须能被 LangGraph 读懂并路由，而不是只有“看起来像答案”的自然语言。
- 每个 Agent 只负责自己那一层，避免一个节点既做规划又做生成又做审查。
- Skill Executor 只负责调用工具，不负责写作判断。
- Verifier / Safety Reviewer / 主控 Agent 的最终裁决要明确区分：
  - Verifier 看“有没有满足任务”
  - Safety Reviewer 看“能不能安全落库/分享”
  - 主控 Agent 看“整体是否值得进入写入”
- Finalizer 不做新的业务推理，只把前面结果封装成交付对象。

回退逻辑建议和 Agent 输出字段绑定，而不是写死某些关键词：

- `ValidationReport.route_back_to = "Content Writer"`
- `ValidationReport.route_back_to = "Planner"`
- `SafetyReport.route_back_to = "HTML Coder"`
- `SafetyReport.route_back_to = "Finalizer"` 或直接终止

这样 LangGraph 只需根据结构化报告做条件边，而不是 Runtime 硬判断业务内容。

已确认的补充决策：需要一个主控 Agent，但它不等于 Runtime。

- 主控 Agent / Orchestrator / 调度智能体 负责语义级调度：理解当前阶段、决定调用哪个子 Agent、汇总各节点结果、决定是否回退或收敛，并承担最终验收裁决。
- Runtime 负责硬控制：任务启动、状态持久化、超时、重试、并发限制、成本上限、工具权限、写入权限。
- 子 Agent 负责专业能力：需求分析、规划、写作、样式设计、HTML 编码、验证、安全审查。
- 这一层结构更接近“主控 Agent + 子 Agent 群 + 受控 Runtime”，而不是把所有逻辑压成一个大 Agent。

主控 Agent 的建议职责：

```text
Orchestrator / 主控 Agent
  -> 读入当前 GenerationState
  -> 判断现在该调用哪个子 Agent
  -> 把子 Agent 输出汇总为新的状态
  -> 根据 ValidationReport / SafetyReport 决定回退或继续
  -> 输出最终是否进入 Finalizer
```

主控 Agent 不建议承担的职责：

- 不建议做文件落盘。
- 不建议决定 HTML 的具体业务内容细节。
- 不建议替代 Runtime 做超时、持久化、并发控制、权限控制。
- 不建议把所有工具调用都写成硬编码规则。
- 不建议把最终裁决再拆成一个固定子 Agent；第一版由主控 Agent 兼任更清晰。

更适合的分层理解：

```text
Runtime
  -> 管进程、任务、状态、工具权限、写入权限

Orchestrator / 主控 Agent
  -> 管语义调度、回退、收敛、子 Agent 编排

Sub Agents
  -> 管专业产出
```

## 当前阻碍 / 注意事项

- 不要急于实现。当前阶段是架构讨论和决策记录。
- 不要把“多 Agent”误做成几个函数名或几个 prompt 文件；需要有清晰状态、Agent 角色、输入输出 schema、工具边界、验证与回退机制。
- 不要用 ReAct 单循环替代完整生成工作流。ReAct 是推理-行动模式，适合工具调用策略，但不足以承担长链路产物生成的全部工程治理。
- 不要让 Agent 直接写文件。生成最终应产出结构化 proposal，由受控写入层落盘。
- 不要为了早期节省成本而砍掉关键 Agent 节点或把业务判断塞回 Runtime。生成模块先追求效果稳定，再做成本治理。
- 当前 `html_generation_graph.py` 是早期 beta 生成图，可作为迁移对象，不应视为最终架构。

## 阶段性整理：AI HTML 生成架构当前定稿

### 1. 总体架构

当前确认采用：

```text
受控 Runtime
  -> LangGraph 状态图
      -> Orchestrator / 主控 Agent
          -> 子 Agent 群
          -> Skill Executor / 技能与工具执行器
      -> Finalizer / 交付封装器
  -> Write Gateway / 受控写入层
```

核心原则：

- LangGraph 负责状态图、节点编排、条件路由、循环回退和 trace。
- Runtime 负责任务硬控制，不参与业务判断。
- Orchestrator / 主控 Agent 负责语义调度和最终裁决。
- 子 Agent 负责专业产出。
- Skill Executor 负责受控调用工具。
- Write Gateway 负责最终写入资料库、metadata、build 和审计。

### 2. Runtime 边界

Runtime 可以做：

- 启动任务、保存状态、记录日志。
- 控制超时、重试、并发、成本上限。
- 限制工具权限、文件路径、文件大小、写入权限。
- 根据结构化报告执行 LangGraph 条件边。
- 执行少量确定硬规则，例如安全策略、路径白名单、文件大小上限。

Runtime 不应做：

- 不写死业务关键词。
- 不判断“内容应该怎么写”。
- 不替代 Agent 规划、写作、设计、验证。
- 不为了早期节省成本砍掉关键 Agent 节点。

### 3. Agent 配置

第一版保留这些子 Agent / 节点：

```text
Ingest / Parser / 文档接入与解析器
Requirement Analyst / 需求分析智能体
Planner / 方案规划智能体
Content Writer / 内容写作智能体
Style Designer / 样式设计智能体
HTML Coder / HTML 编码智能体
Skill Executor / 技能与工具执行器
Verifier / 需求达成验证智能体
Safety Reviewer / 安全审查智能体
Finalizer / 交付封装器
```

不再单独设置固定的 `Final Reviewer / 最终验收智能体`：

- 最终验收裁决交给 `Orchestrator / 主控 Agent`。
- `Finalizer / 交付封装器` 不做业务推理，只封装 `CreateNoteProposal / 创建笔记提案`。

### 4. 主控 Agent

`Orchestrator / 主控 Agent` 的职责：

- 读取当前 `GenerationState / 生成状态`。
- 决定调用哪个子 Agent。
- 汇总子 Agent 的结构化输出。
- 根据 `ValidationReport / 需求验证报告` 和 `SafetyReport / 安全审查报告` 决定继续、回退、终止或进入交付。
- 最终判断是否进入 `Finalizer / 交付封装器`。

主控 Agent 不做：

- 不直接落盘。
- 不替代 Runtime 做超时、并发、权限控制。
- 不把工具调用写成硬编码业务规则。

### 5. 文档解析层

第一阶段输入类型：

- HTML
- Markdown
- TXT
- PDF
- Word
- PPT

第二阶段再考虑：

- Excel
- 通过链接生成
- 复杂网页抓取
- 扫描件 PDF / 图片型文档
- 复杂 PPT 动画或版式

解析链路：

```text
安全检查
  -> MarkItDown 主解析
  -> 本地轻量解析兜底
  -> 失败并返回 warning
```

当前决定：

- 第一阶段不引入大量专业解析工具。
- MarkItDown 作为通用解析主力。
- 本地轻量解析用于 HTML / Markdown / TXT 等兜底。
- 第一阶段不设计“要求用户补充材料”的新交互；解析不足只写入 warnings。
- 基础解析默认由 Runtime / Ingest 执行。
- 深度解析、补充解析、样式线索提取可由 Agent 通过 Skill Executor 按需调用。

### 6. Skill Executor

`Skill Executor / 技能与工具执行器` 的作用：

- 把 Agent 想调用的能力变成受控工具执行。
- 检查权限、调用工具、处理失败、做降级、返回结构化结果。
- 它不是写作 Agent，也不是规划 Agent。

典型调用：

- MarkItDown 解析。
- 本地 HTML / Markdown / TXT 解析。
- 样式线索提取。
- 本地知识库检索。
- 外部搜索。
- HTML 安全扫描。

解析相关的最终理解：

```text
Ingest / 基础接入解析
  -> 默认必跑，确保任务有基础输入

Skill Executor / 技能工具执行器
  -> 按 Agent 需求做补充解析和其他工具调用
```

### 7. 中间产物

所有关键节点应输出结构化对象：

```text
ParsedDocument / 解析后的文档
RequirementBrief / 需求简报
PlanDraft / 方案草案
ContentDraft / 内容草稿
StyleBrief / 样式简报
HtmlDraft / HTML 草稿
ValidationReport / 需求验证报告
SafetyReport / 安全审查报告
CreateNoteProposal / 创建笔记提案
```

回退应基于结构化字段：

```text
ValidationReport.route_back_to = "Content Writer"
ValidationReport.route_back_to = "Planner"
SafetyReport.route_back_to = "HTML Coder"
```

### 8. 异步任务与状态

AI 生成必须是异步任务。用户提交文件和需求后，可以离开页面继续做其他事情。

需要提供任务队列 / 生成历史 / 状态页，状态至少预留：

```text
queued / 等候中
parsing / 解析中
parse_failed / 解析失败
analyzing_requirements / 分析需求中
planning / 规划中
writing_content / 撰写内容中
executing_skills / 调用技能中
designing_style / 设计样式中
coding_html / 生成 HTML 中
verifying / 验证中
safety_checking / 安全检查中
finalizing / 收尾中
writing / 写入资料库中
completed / 已完成
failed / 失败
canceled / 已取消
```

加分项：

- 任务详情可展示 AI 处理过程 / 阶段回放 / Agent 正在做什么。
- 页面保持项目统一风格，不追求花哨。
- 当前仅记录需求，不展开具体规划。

### 9. 写入与默认落库

生成结果默认：

- 写入资料库。
- 默认 collection = `inbox`。
- 通过 `Write Gateway / 受控写入层` 执行。
- Agent 只输出 `CreateNoteProposal / 创建笔记提案`，不直接写文件。

### 11. 已确认：RequirementBrief / 需求简报

作用：把用户输入、文件内容、前端选项转成明确需求，回答“用户要什么”。

建议字段：

```text
RequirementBrief / 需求简报
  - user_goal / 用户目标
  - target_use / 目标用途
  - audience / 目标读者
  - output_type / 输出类型
  - source_summary / 原始资料摘要
  - must_include / 必须包含
  - should_avoid / 应避免
  - constraints / 约束条件
  - style_preferences / 样式偏好
  - reference_style_files / 参考样式文件
  - success_criteria / 成功标准
  - uncertainty / 不确定点
```

边界：

- 由 `Requirement Analyst / 需求分析智能体` 产出。
- 不负责规划页面结构。
- 不直接写正文。
- `success_criteria / 成功标准` 是后续 `Verifier / 需求达成验证智能体` 的重要依据。

### 12. 已确认：PlanDraft / 方案草案

作用：把需求简报转成可执行生成方案，回答“我们怎么做”。

建议字段：

```text
PlanDraft / 方案草案
  - page_goal / 页面目标
  - information_architecture / 信息架构
  - section_plan / 章节规划
  - content_strategy / 内容策略
  - visual_strategy / 视觉策略
  - tool_needs / 需要调用的工具
  - execution_checklist / 执行清单
  - risk_points / 风险点
  - verification_targets / 验证目标
```

边界：

- 由 `Planner / 方案规划智能体` 产出。
- 输入为 `RequirementBrief / 需求简报` + `ParsedDocument / 解析后的文档`。
- 不直接写正文。
- 不直接生成 HTML。
- `tool_needs / 需要调用的工具` 可交给 `Skill Executor / 技能与工具执行器` 处理。
- `execution_checklist / 执行清单` 是 LangGraph 质量控制骨架，后续节点需要逐项更新状态。

### 13. 已确认的需求分析与规划原则

```text
Requirement Analyst / 需求分析智能体
  -> 输出 RequirementBrief / 需求简报
  -> 不规划页面结构

Planner / 方案规划智能体
  -> 输入 RequirementBrief / 需求简报 + ParsedDocument / 解析后的文档
  -> 输出 PlanDraft / 方案草案
  -> 不直接写正文
```

结论：

- 需求分析负责“用户要什么”。
- 方案规划负责“我们怎么做”。
- 写作、样式设计、HTML 生成由后续子 Agent 执行。

### 14. 已确认：Execution Checklist / 执行清单

`Planner / 方案规划智能体` 需要输出 `execution_checklist / 执行清单`，不能只输出页面结构。每个后续 Agent 完成自己的工作后，应更新清单状态；`Verifier / 需求达成验证智能体` 和 `Orchestrator / 主控 Agent` 按清单验收与回退。

示例结构：

```text
execution_checklist:
  - id: "parse-source"
    title: "确认源文件主要内容已提取"
    owner: "Ingest"
    status: "done"
    acceptance: "ParsedDocument.plain_text 非空，outline 或 source_summary 可用"

  - id: "clarify-requirement"
    title: "明确用户目标和输出类型"
    owner: "Requirement Analyst"
    status: "pending"
    acceptance: "RequirementBrief.user_goal、output_type、success_criteria 已填写"

  - id: "draft-content"
    title: "完成页面正文草稿"
    owner: "Content Writer"
    status: "pending"
    acceptance: "ContentDraft.sections 覆盖 PlanDraft.section_plan"

  - id: "apply-style"
    title: "完成视觉样式方案"
    owner: "Style Designer"
    status: "pending"
    acceptance: "StyleBrief.colors、typography、layout 与用户偏好一致"

  - id: "build-html"
    title: "生成完整 HTML"
    owner: "HTML Coder"
    status: "pending"
    acceptance: "HtmlDraft.html 是完整、可渲染、无明显布局断裂的 HTML"

  - id: "verify"
    title: "逐项验证需求达成"
    owner: "Verifier"
    status: "pending"
    acceptance: "ValidationReport.ok = true"
```

与 LangGraph 的关系：

```text
GenerationState / 生成状态
  - plan_draft / 方案草案
  - execution_checklist / 执行清单
  - current_step / 当前步骤
  - completed_steps / 已完成步骤
  - failed_steps / 失败步骤
```

设计价值：

- Planner 先定义“什么算完成”。
- 子 Agent 不再自由发挥，而是按清单推进。
- Verifier 可以逐项验收，不是泛泛评价。
- 主控 Agent 可以看到哪里未完成或不达标。
- 回退时可以只回退某个未达标节点，而不是整条链重跑。

### 15. 进入讨论：StyleBrief / 样式简报与样式生成逻辑

样式设计是 AI HTML 生成质量的关键环节，不能简单理解为“套模板”或“照抄上传样式文件”。当前讨论方向：

```text
Style Designer / 样式设计智能体
  -> 保留大模型自主设计能力
  -> 结合用户显式约束
  -> 参考用户上传样式文件
  -> 可按需调用开源 HTML 设计项目 / skill
  -> 输出 StyleBrief / 样式简报
```

建议的 `StyleBrief / 样式简报` 字段：

```text
StyleBrief / 样式简报
  - style_goal / 样式目标
  - design_mode / 设计模式
  - reference_sources / 参考来源
  - color_palette / 色彩方案
  - typography / 字体与字号
  - layout_system / 布局系统
  - component_style / 组件风格
  - density / 信息密度
  - visual_hierarchy / 视觉层级
  - interaction_level / 交互程度
  - responsive_rules / 响应式规则
  - avoid_styles / 应避免的样式
  - implementation_notes / 实现注意事项
```

需要保留三类样式生成模式：

```text
default_free_design / 默认自由设计
  -> 无参考、无强约束时，由大模型根据内容和目标用途自主设计

constrained_design / 有约束设计
  -> 用户选择了 theme、style_preference、target_use 或文本明确要求

reference_guided_design / 参考引导设计
  -> 用户上传样式文件，或后续接入开源设计项目 / skill
```

核心原则：

- 不要默认套死模板。无参考无约束时，应允许大模型发挥设计能力。
- 有用户明确要求时，用户要求优先。
- 有参考样式文件时，做风格抽象，不做像素级复刻。
- 有开源 HTML 设计项目或 skill 时，应作为参考/生成辅助，不应绑死主链路。
- 样式链路要服务业务结果：可读、好看、稳定、安全、能落库，而不是追求炫技。

样式参考文件处理逻辑：

```text
上传样式文件
  -> Ingest / 基础解析
  -> 提取 style_hints / 样式线索
  -> Style Designer 判断参考价值
  -> 输出风格抽象后的 StyleBrief
```

开源项目 / skill 的预留逻辑：

```text
Style Designer 判断需要外部设计能力
  -> 在 PlanDraft.tool_needs 或 StyleBrief.reference_sources 中声明
  -> Orchestrator 允许后
  -> Skill Executor 受控调用对应设计 skill / 工具
  -> 返回 DesignReference / 设计参考结果
  -> Style Designer 融合为 StyleBrief
```

这里需要后续单独仔细设计：

- 哪些开源 HTML 设计项目适合接入。
- 哪些能力做成本地 skill。
- 哪些只是作为提示词参考或样式库。
- 是否允许生成过程中拉取远程模板。
- 如何避免版权、品牌、外链、安全风险。
- 后续使用开源项目时必须审查开源协议，避免把不兼容 license 的代码、模板、素材或依赖引入生成链路或产物。
- 如何避免工具结果压过大模型自身设计能力。

当前初步判断：

- 第一版先保留接口与业务逻辑，不急着绑定具体开源项目。
- 默认能力应是“大模型自主设计 + 结构化 StyleBrief”。
- 开源项目 / skill 是增强项，不是核心依赖。

补充设计：谁决定是否调用开源项目 / skill。

建议采用“两段式决策”：

```text
Planner / 方案规划智能体
  -> 根据需求判断是否可能需要额外设计能力
  -> 写入 PlanDraft.tool_needs

Orchestrator / 主控 Agent
  -> 结合任务状态、成本、权限、可用工具、安全策略做最终调度
  -> 决定是否让 Skill Executor 调用对应 skill / 开源项目封装

Style Designer / 样式设计智能体
  -> 如果没有外部参考，负责托底自主设计
  -> 如果有 DesignReference，负责融合参考并输出 StyleBrief
```

也就是说：

- `Style Designer / 样式设计智能体` 不是唯一决策者，更像“自主设计 + 融合参考”的专业 Agent。
- 是否调用外部设计能力，应由 `Planner / 方案规划智能体` 提出需求，`Orchestrator / 主控 Agent` 做最终调度。
- `Skill Executor / 技能与工具执行器` 只执行被允许的调用，不做业务判断。

补充设计：开源项目与 skill 的业务分层。

```text
Open-source Project / 开源项目
  -> 外部能力来源
  -> 可能是模板库、组件库、设计生成器、HTML/CSS 工具、截图/渲染工具
  -> 需要 license 审查、安全审查、依赖审查

Skill / 技能
  -> 项目内部封装层
  -> 对开源项目或本地逻辑做统一接口、输入输出 schema、权限控制、降级策略
  -> 给 Agent 暴露的是 skill，不是原始开源项目
```

建议不要让 Agent 直接调用原始开源项目。更合理的是：

```text
Agent / 主控或子 Agent
  -> 请求 design_skill
  -> Skill Executor 检查权限
  -> skill 内部调用某个开源项目或本地实现
  -> 返回 DesignReference / 设计参考结果
```

这样开源项目可以替换，Agent 层不需要知道底层具体实现。

### 16. 已确认：统一术语为 tools 与 skill

本轮讨论中发现 `skill` 一词存在两种含义。为避免后续设计和代码命名混乱，后续统一拉平为：

```text
tools / 工具
  -> 可执行工具能力、脚本、开源项目封装、外部 API、解析器、安全扫描器

skill / 技能
  -> Markdown 驱动的大模型工作方法包，按需披露、按需加载
```

也就是说，后续不再使用 `Tool Skill / 工具能力型 Skill` 这类说法，直接称为 `tools / 工具`。

#### A. tools / 工具

这是前文 `Skill Executor / 技能与工具执行器` 实际要执行的东西，更接近受控工具、脚本、开源项目封装或能力 API。

定位：

```text
tools / 工具
  -> 受控工具能力
  -> 由 Tool Executor / 工具执行器调用
  -> 输入输出结构化
  -> 可审计、可降级、可替换
```

例子：

- OCR 解析。
- 高级 PDF 解析。
- 样式线索提取。
- 外部搜索。
- 截图渲染检查。
- HTML 安全扫描。

#### B. skill / 技能

这是用户强调的 skill：由 Markdown 文件驱动的大模型工作流，支持按需披露、按需加载，更像一套可复用的专家说明书 / 工作方法 / 生成策略。

定位：

```text
skill / 技能
  -> Markdown 驱动
  -> 给 Agent 提供方法论、约束、示例和流程
  -> 按需加载，避免上下文污染
  -> 不直接执行程序
```

例子：

- HTML 页面设计 skill。
- 商业报告写作 skill。
- 科普解释写作 skill。
- 投研风格总结 skill。
- 移动端响应式设计 skill。

#### 两者关系

```text
skill / 技能
  -> 告诉 Agent 应该如何思考、如何写、如何设计

tools / 工具
  -> 帮 Agent 受控执行某个外部能力
```

二者都可以被主控 Agent 或子 Agent 使用，但用途不同：

- skill 影响 Agent 的推理和生成策略。
- tools 执行具体工具能力。

后续建议命名：

```text
Skill Loader = 负责按需加载 Markdown 驱动的 skill
Tool Executor = 负责执行 tools
Skill Executor = 历史表述，后续建议逐步改名为 Tool Executor
```

当前结论：

- 前文提到的“默认核心技能包”需要重新审视，不能把 tools 与 skill 混为一谈。
- LangGraph 本身不是 skill。
- HTML 生成工作流可以按需加载 skill，也可以通过 Tool Executor 调用 tools。

### 17. 已确认：skill 是否介入当前智能体架构

结论：需要，但不作为主架构介入，而是作为 Agent 的专业知识扩展层介入。

当前主架构仍然是：

```text
LangGraph
  -> Orchestrator / 主控 Agent
  -> 子 Agent
  -> tools / 工具
  -> Write Gateway / 受控写入层
```

skill 的合理位置：

```text
Agent 执行前
  -> Skill Loader 判断是否加载某个 skill
  -> 把 skill 中的方法论、约束、示例注入该 Agent 的上下文
  -> Agent 按专业方法完成自己的节点任务
```

适合加载 skill 的节点：

```text
Style Designer / 样式设计智能体
  -> 加载 HTML 页面设计 skill
  -> 加载响应式布局 skill

Content Writer / 内容写作智能体
  -> 加载商业报告写作 skill
  -> 加载科普解释写作 skill

HTML Coder / HTML 编码智能体
  -> 加载安全静态 HTML 约束 skill

Verifier / 需求达成验证智能体
  -> 加载内容质量评审 skill
```

skill 不适合做：

- 不控制 LangGraph 主流程。
- 不决定任务状态。
- 不直接调用 tools。
- 不直接写文件。
- 不替代 Orchestrator / 主控 Agent。

第一版建议：

- 不大量加载 skill，避免上下文污染。
- 只给关键 Agent 加少量基础 skill。
- 可优先考虑：
  - `Style Designer / 样式设计智能体`：HTML 页面设计方法。
  - `HTML Coder / HTML 编码智能体`：安全静态 HTML 约束。
  - `Verifier / 需求达成验证智能体`：质量验收方法。

### 18. 已确认：ContentDraft / 内容草稿 与 HtmlDraft / HTML 草稿边界

核心原则：不要让 `HTML Coder / HTML 编码智能体` 一边想内容、一边想结构、一边写代码。内容、样式、实现必须分层。

```text
Content Writer / 内容写作智能体
  -> 只负责内容
  -> 输出 ContentDraft / 内容草稿

Style Designer / 样式设计智能体
  -> 只负责样式方案
  -> 输出 StyleBrief / 样式简报

HTML Coder / HTML 编码智能体
  -> 输入 ContentDraft / 内容草稿 + StyleBrief / 样式简报 + PlanDraft / 方案草案
  -> 只负责实现为 HTML
  -> 输出 HtmlDraft / HTML 草稿
```

`ContentDraft / 内容草稿` 建议字段：

```text
ContentDraft / 内容草稿
  - title / 标题
  - subtitle / 副标题
  - summary / 摘要
  - sections / 内容章节
  - key_points / 关键要点
  - callouts / 重点提示
  - tables / 表格内容
  - quotes / 引用内容
  - references_used / 使用的来源
  - omitted_items / 未使用或省略的内容
```

ContentDraft 边界：

- 不包含 CSS。
- 不写 HTML。
- 可以包含结构化章节、表格、提示块。
- 要说明哪些原始资料被使用，哪些被省略。

`HtmlDraft / HTML 草稿` 建议字段：

```text
HtmlDraft / HTML 草稿
  - html / 完整 HTML
  - assets / 资源引用
  - css_notes / CSS 说明
  - js_notes / JS 说明
  - render_assumptions / 渲染假设
  - accessibility_notes / 可访问性说明
  - responsive_notes / 响应式说明
```

HtmlDraft 边界：

- `HTML Coder / HTML 编码智能体` 不重新发明内容。
- 可以做必要文案微调，但不能改变事实和结构。
- 如果发现内容不足，应返回给主控 Agent，由主控 Agent 回退到 `Content Writer / 内容写作智能体`。
- 如果发现样式难以实现，应回退到 `Style Designer / 样式设计智能体`。
- 如果发现结构不适合 HTML，应回退到 `Planner / 方案规划智能体`。

硬约束：

```text
HTML Coder / HTML 编码智能体 不负责业务内容判断，只负责实现。
```

问题归因：

```text
内容问题 -> 回 Content Writer / 内容写作智能体
结构问题 -> 回 Planner / 方案规划智能体
样式问题 -> 回 Style Designer / 样式设计智能体
代码问题 -> 回 HTML Coder / HTML 编码智能体
```

### 19. 已确认：验证、回退与安全门禁

本阶段确认 `Verifier / 需求达成验证智能体`、`Safety Reviewer / 安全审查智能体` 和 `Orchestrator / 主控 Agent` 的最终裁决边界。

#### Verifier / 需求达成验证智能体

作用：检查生成内容是否满足用户需求。只判断需求达成，不判断安全。

输入：

```text
RequirementBrief / 需求简报
PlanDraft / 方案草案
Execution Checklist / 执行清单
ContentDraft / 内容草稿
StyleBrief / 样式简报
HtmlDraft / HTML 草稿
ParsedDocument / 解析后的文档
```

输出：

```text
ValidationReport / 需求验证报告
  - ok / 是否通过
  - score / 质量评分
  - checked_items / 已检查项
  - issues / 问题列表
  - missing_parts / 缺失内容
  - unsupported_claims / 无依据内容
  - style_mismatch / 样式不匹配
  - structure_mismatch / 结构不匹配
  - route_back_to / 回退节点
  - retry_instruction / 重试说明
```

#### Safety Reviewer / 安全审查智能体

作用：检查能不能安全落库/分享。

输入：

```text
HtmlDraft / HTML 草稿
CreateNoteProposal / 创建笔记提案
Share policy / 分享安全规则
```

输出：

```text
SafetyReport / 安全审查报告
  - ok / 是否通过
  - risk_level / 风险等级
  - issues / 问题列表
  - blocked_items / 阻断项
  - warnings / 警告
  - route_back_to / 回退节点
  - requires_user_confirmation / 是否需要用户确认
```

Safety Reviewer 重点检查：

- 危险 script。
- 不安全外链。
- 隐私泄漏。
- 违反分享安全策略。
- 过大的内联资源。
- 不受控 iframe / form / tracking。

#### Orchestrator / 主控 Agent 最终裁决

主控 Agent 不重新做全部审查，而是汇总报告后裁决：

```text
ValidationReport.ok && SafetyReport.ok
  -> Finalizer / 交付封装器

ValidationReport 不通过
  -> route_back_to 对应节点

SafetyReport 不通过且可修复
  -> HTML Coder / HTML 编码智能体 或 Style Designer / 样式设计智能体

SafetyReport 高风险
  -> 终止或要求用户确认
```

#### 回退规则

```text
内容缺失 -> Content Writer / 内容写作智能体
结构不合理 -> Planner / 方案规划智能体
样式不符 -> Style Designer / 样式设计智能体
HTML 实现问题 -> HTML Coder / HTML 编码智能体
安全问题可修复 -> HTML Coder / HTML 编码智能体
安全问题不可修复 -> 终止 / 等用户确认
资料不足 -> Planner / 方案规划智能体 或 Content Writer / 内容写作智能体
```

#### 循环控制

开发阶段不优先节省模型成本，但必须防止无限循环：

```text
max_revision_rounds: 3
max_same_node_retries: 2
hard_stop_on_high_risk: true
```

Runtime 只做这些硬控制，不参与业务判断。

### 20. 已确认：Write Gateway / 受控写入层

`Write Gateway / 受控写入层` 是 Agent 和真实文件系统之间的边界。Agent 不直接写文件，只输出 `CreateNoteProposal / 创建笔记提案`。

定位：

```text
Write Gateway / 受控写入层
  -> 接收 CreateNoteProposal / 创建笔记提案
  -> 做最终硬规则校验
  -> 写 HTML 文件
  -> 写 metadata
  -> 触发 build / index
  -> 记录审计日志
  -> 返回最终 item_id / run_id
```

它不是 Agent，不做业务判断。

输入结构：

```text
CreateNoteProposal / 创建笔记提案
  - title / 标题
  - html / HTML 内容
  - metadata / 元数据
  - target_collection / 目标集合
  - tags / 标签
  - source_files / 来源文件
  - source_links / 来源链接
  - safety_summary / 安全摘要
  - generation_trace_id / 生成链路 ID
```

默认值：

```text
target_collection = "inbox"
source_type = "ai_generated"
```

Write Gateway 负责：

```text
- 校验 HTML 大小
- 校验路径安全
- 校验文件名
- 校验 metadata 字段
- 校验 target_collection，默认 inbox
- 调用已有 HTML 安全扫描
- 清理或拒绝危险 HTML
- 写入 content 目录
- 写入 metadata
- 触发 build_site / 更新 manifest
- 写入 run/job 审计记录
```

Write Gateway 不负责：

```text
- 不重写正文
- 不重新规划页面
- 不决定样式好不好
- 不调用 LLM
- 不绕过 SafetyReport / 安全审查报告
```

失败处理：

```text
HTML 安全失败
  -> 返回 SafetyWriteError
  -> 主控 Agent 可决定回 HTML Coder 或终止

路径 / 文件名失败
  -> Gateway 自动生成安全文件名

metadata 失败
  -> 尝试规范化
  -> 仍失败则返回 MetadataWriteError

build 失败
  -> 文件先不提交或回滚
  -> 返回 BuildError
```

回滚策略：

第一版理想策略：

```text
先写临时文件
  -> metadata 临时写入
  -> build 验证
  -> 全部成功后原子提交
```

如果实现成本较高，第一版至少要做到：

```text
写 HTML 成功但 metadata / build 失败
  -> 删除刚写入的 HTML
  -> 不留下半成品
```

设计价值：

- Agent 不直接拥有文件系统写权限。
- 所有 AI 生成内容统一走安全门禁。
- 后续 AI 修改现有笔记时也能复用。
- 生成失败不会污染资料库。
- run / job 历史可追踪、可回滚。

一句话定位：

> Write Gateway 是 AI 产物进入资料库前的最后一道工程边界。

### 21. 已确认：模型配置策略

第一版统一使用 `gpt-5.5`，不在开发初期做分节点降模型或成本压缩。

原则：

- HTML 生成是核心能力，第一阶段优先质量和架构正确性。
- 所有 Agent 节点第一版默认使用同一主模型：`gpt-5.5`。
- 后续保留拓展接口，允许按节点配置模型，例如：
  - `Requirement Analyst / 需求分析智能体`
  - `Planner / 方案规划智能体`
  - `Content Writer / 内容写作智能体`
  - `Style Designer / 样式设计智能体`
  - `HTML Coder / HTML 编码智能体`
  - `Verifier / 需求达成验证智能体`
  - `Safety Reviewer / 安全审查智能体`
- 后续可做成本优化：
  - 低风险节点降模型。
  - 失败重试时升模型。
  - 审查节点按复杂度选择模型。
  - 缓存解析、规划、样式中间结果。

建议配置结构预留：

```text
GenerationModelProfile / 生成模型配置
  - default_model: "gpt-5.5"
  - node_models:
      requirement_analyst: null
      planner: null
      content_writer: null
      style_designer: null
      html_coder: null
      verifier: null
      safety_reviewer: null
  - retry_policy:
      allow_model_escalation: false
      escalation_model: null
```

第一版实现时可以只读 `default_model`，但结构要留好。

### 26. 建议方案：测试验收标准

第一版至少准备以下真实样例：

```text
Markdown 文件 -> 生成结构清晰 HTML
HTML 文件 -> 提取原内容并重组
PDF 文件 -> 生成摘要/讲解型 HTML
Word 文件 -> 生成报告型 HTML
PPT 文件 -> 生成展示型 HTML
带样式参考文件 -> 风格明显受参考影响
解析 warning -> 能保守生成且记录 warning
安全失败样例 -> 被 Safety Reviewer / Write Gateway 阻断
回退样例 -> Verifier 能让内容或样式节点重跑
```

验收维度：

- 是否按用户需求生成。
- 是否覆盖原始资料核心内容。
- 是否结构清晰。
- 是否视觉质量合格。
- 是否移动端可读。
- 是否通过安全检查。
- 是否正确进入资料库 `inbox`。
- 是否有 job/run/stage trace。

测试层级：

```text
单元测试
  -> schema 校验、Store、Write Gateway、安全扫描

集成测试
  -> generation_v2 graph 跑通

端到端测试
  -> 上传文件 -> 异步任务 -> 状态变化 -> 生成笔记 -> 打开阅读页

人工真实验收
  -> 多格式文件 + 样式参考 + 复杂需求
```

第一版交付标准：

- 至少 Markdown / HTML / PDF 跑通。
- 至少一个样式参考场景可见效果。
- 至少一个安全失败场景被阻断。
- 任务状态与结果落库可见。
