**时间**：2026-06-18 13:42 JST

## 目标

实现 AI HTML 生成 v2：用户上传文件并输入需求后，系统通过 LangGraph 多 Agent 协作生成 HTML 文件，异步写入资料库，默认进入 `inbox` 集合，并在前端生成历史/任务队列中展示状态。

第一版优先目标：

- 架构正确。
- 生成质量优先。
- Runtime 不参与业务判断。
- 各模块解耦，后续可复用于 AI 修改、基于问答生成笔记、知识库管理。
- 保留 legacy fallback，避免破坏现有功能。

## 总体架构

```text
API / Runtime
  -> GenerationStore / 生成任务存储
  -> LangGraph generation_v2
      -> Orchestrator / 主控 Agent
          -> Requirement Analyst / 需求分析智能体
          -> Planner / 方案规划智能体
          -> Content Writer / 内容写作智能体
          -> Style Designer / 样式设计智能体
          -> HTML Coder / HTML 编码智能体
          -> Verifier / 需求达成验证智能体
          -> Safety Reviewer / 安全审查智能体
      -> Ingest / Parser / 文档接入与解析器
      -> Tool Executor / 工具执行器
      -> Skill Loader / 技能加载器
      -> Finalizer / 交付封装器
  -> Write Gateway / 受控写入层
  -> inbox
```

术语约定：

- `tools / 工具`：可执行能力，例如解析器、搜索、HTML 安全扫描、截图检查。
- `skill / 技能`：Markdown 驱动的大模型方法包，按需加载，不直接执行程序。
- `Tool Executor / 工具执行器`：执行 tools。
- `Skill Loader / 技能加载器`：加载 Markdown skill。
- `Runtime`：任务、状态、权限、超时、重试、写入边界，不做业务判断。

## 文档解析实现

`Ingest / Parser` 是固定节点，不是 skill。

第一版链路：

```text
安全检查
  -> MarkItDown 主解析
  -> 本地轻量解析兜底
  -> 失败写入 warnings
```

工具位置：

```text
generation_v2/tools/document_parser.py
```

输入：

```text
filename
content bytes
content_type
reference_style_file optional
```

输出：

```text
ParsedDocument
```

要求：

- 限制文件大小。
- 仅解析上传到受控临时位置的文件。
- 禁止任意本地路径。
- 默认禁止外部 URL 解析。
- MarkItDown 不可用时降级本地轻量解析。

### Decision Gate 2 / 决策点：MarkItDown 依赖

实现前需要确认：

- 是否把 `markitdown` 加入 agent extra 依赖。
- 是否允许第一版仅在安装了 `markitdown` 时增强解析，未安装则降级。
- 是否需要把 Office/PDF 解析失败提示写入 warnings。

建议默认：加入 agent extra 依赖，但保留 import guard 和降级。

已确认并实现：

- `markitdown[pdf,docx,pptx,xlsx,xls]` 加入 `agent` optional dependencies；与 LangGraph 一样作为第三方开源依赖安装，不把源码复制进仓库。
- 不使用 `markitdown[all]`，避免把 YouTube、Azure、音频转写等需要外部服务或非第一阶段能力的依赖拖入默认安装。
- 第一版默认 `HTML_LORE_DOCUMENT_PARSER=markitdown`，即启用增强文档解析。
- 可设置 `HTML_LORE_DOCUMENT_PARSER=basic` 关闭增强解析，适用于轻量部署或解析问题排障。
- `document_parser` 保留 import guard。
- HTML / Markdown / TXT 使用本地轻量解析。
- PDF / Word / PPT / Excel / CSV / JSON / 图片元数据 / EPUB / Notebook / ZIP / RSS 等本地文件型 converter 优先尝试 MarkItDown，失败或未安装时降级本地基础解析并写入 `warnings`。
- URL、OCR、音频、YouTube、Azure 解析等第二阶段输入不因 MarkItDown 默认启用而提前开放；第一版未确认格式直接基础兜底并提示 unsupported。
- MarkItDown 按解析任务调用受控上传内容生成的临时文件；第一版不启用插件、不解析 URL、不允许任意本地路径或任意 IO 权限。

资源与部署约束：

- 增强解析会消耗 CPU、内存和临时磁盘，尤其是大 PDF / PPT / Word。
- 第一版依赖现有上传大小限制，并保留失败降级。
- 后续 `doctor` 需要检查 LangGraph、MarkItDown、文件解析 smoke test、可用内存/临时目录。
- 后续生产部署建议将 AI 解析/生成任务放入独立 worker，并增加解析超时与并发限制。

## Agent 实现策略

每个 Agent 文件负责：

```text
读取当前 GenerationState
加载 prompt
按需加载 skill
调用 LLM
解析结构化输出
校验 schema
写回 state
更新 execution_checklist
追加 stage_trace
```

第一版 Agent：

```text
Requirement Analyst
Planner
Content Writer
Style Designer
HTML Coder
Verifier
Safety Reviewer
Finalizer
```

主控 Agent：

```text
Orchestrator
  - 根据 state 决定下一节点
  - 根据 ValidationReport / SafetyReport route_back_to 回退
  - 控制 revision_round
  - 最终决定进入 Finalizer
```

硬约束：

- HTML Coder 不做业务内容判断。
- Finalizer 不做业务推理。
- Safety Reviewer 不绕过 Write Gateway。

### Decision Gate 3 / 决策点：Agent 输出解析方式

需要确认：

- 使用模型 JSON 输出 + Pydantic 校验。
- 失败时是否重试同节点。
- schema 失败是否计入 same_node_retries。

建议默认：强制 JSON schema，解析失败重试同节点，超过 2 次失败并标记 retryable。

已确认并实现：

- 使用 JSON schema 风格结构化输出，第一版先通过 dataclass schema 解析和校验。
- 解析失败重试同节点，计入 `same_node_retries`。
- 同一节点超过 2 次 schema 失败后，阶段失败并标记 retryable，不进入后续写入。
- 当前 Phase 3 使用 `FakeGenerationModelClient` 验证 schema 成功、失败重试、超过重试上限三条路径。

## StyleBrief 与样式逻辑

三种设计模式：

```text
default_free_design
constrained_design
reference_guided_design
```

优先级：

```text
用户明确要求 > 安全与可读性 > 目标用途 > 样式文件 > 默认主题
```

第一版不接入开源设计项目，只保留接口。

样式参考文件：

- Ingest 解析基本内容。
- `style_hint_extractor` 提取颜色、布局、语气、标题层级等线索。
- Style Designer 融合为 StyleBrief。
- 不做像素级复刻。

### Decision Gate 6 / 决策点：样式参考文件处理深度

需要确认：

- 第一版是否只提取文件名、文本结构、明显颜色/标题线索。
- 是否需要对 HTML 样式参考解析 CSS。

建议默认：HTML 样式参考可解析内联 CSS/颜色；PDF/PPT/Word 只做文本和风格摘要，不做复杂视觉解析。

已确认并实现：

- 第一版只提取轻量风格线索，不做像素级复刻。
- 新增 `style_hint_extractor`，从解析后的文本中提取颜色、字体、布局关键词、图片元数据等线索。
- HTML/CSS 样式参考可提取明显颜色、font-family、grid/flex/card/table 等布局线索。
- PDF/PPT/Word/Excel/图片等样式参考先经 MarkItDown / 本地解析转文本，再抽取可用线索。
- `GenerationInput.reference_content` 和 `parsed_style_reference` 已进入 v2 schema。
- `StyleDesigner` 在存在 `parsed_style_reference` 时进入 `reference_guided_design`，并把参考线索写入 `StyleBrief.implementation_notes`。
- 当前只是 v2 graph 能力；API 将 reference file bytes 接入 v2 在后续 `material-jobs` 接口接入阶段完成。

## Write Gateway

文件：

```text
generation_v2/write_gateway.py
```

输入：

```text
CreateNoteProposal
```

输出：

```text
item_id
metadata
build_result
audit_summary
```

职责：

- 校验 HTML 大小。
- 校验路径和文件名。
- 生成安全文件名。
- 默认 `target_collection = inbox`。
- 默认 `source_type = ai_generated`。
- 调用 HTML 安全扫描。
- 写 HTML。
- 写 metadata。
- build_site / 更新 manifest。
- 失败回滚。

最低回滚要求：

```text
写 HTML 成功但 metadata/build 失败
  -> 删除刚写入的 HTML
  -> 不留下半成品
```

### Decision Gate 7 / 决策点：Write Gateway 事务策略

需要确认：

- 第一版是否实现临时目录原子提交。
- 还是实现最低回滚策略。

建议默认：先实现最低回滚策略，稳定后再升级临时目录原子提交。

已确认并实现：

- 第一版采用最低回滚策略，不先做完整临时目录原子提交。
- `WriteGateway` 已校验 HTML 为空、标题为空、HTML 大小超过 `max_upload_bytes`。
- 写入路径使用 `generated/YYYY/MM/{slug}.html`，并通过 `ensure_within` 限制在内容目录内。
- 写 HTML、写 metadata、调用 `build_site` 更新 manifest。
- 如果 metadata 或 build 失败，会删除本次刚写入的 HTML；如果 metadata 已写入，也一并删除，避免半成品。
- 当前未在 Write Gateway 内新增完整 HTML 安全扫描；安全扫描仍由 `SafetyReviewer` 与后续 `html_safety` 工具承接。

## 2026-07-01：任务内临时材料检索上下文

背景：

- 生产实测中，多文件上传生成报告时，解析器实际已经提取到了后续文件中的关键表格和数字信息。

- 这不是 MarkItDown 解析失败，而是材料进入 Agent 前的上下文组织问题。

- 不新增独立 Agent 节点。
- 不接入知识库问答 RAG，不写入向量库，不污染知识库上下文。

  - 按空行、标题、幻灯片定位、长度切块。
  - 标记通用结构信号：`table_like`、`numeric_dense`、`structured_heading`、`short_context`。
  - 做 instruction token overlap、表格/数字/标题等通用加权。
  - 做每文件公平覆盖和总字符预算控制。
- Runtime 不判断“价格表是否重要”“供应商是否完整”“哪个业务字段必须保留”，也不写业务关键词白名单或黑名单。这些判断仍交给 RequirementAnalyst / Planner / ContentWriter。

- 新增 `html_lore/server/ai/generation_v2/material_context.py`。

## 2026-07-01：Agent 主导的任务内材料召回

背景：

- `TemporaryMaterialContext` 是一次性预召回，只能缓解长材料前缀截断问题，不能保证多文件、表格密集、数字密集场景下所有关键证据都进入前置上下文。
- 为了保持“LLM/Agent 主导业务判断，runtime 只做工具与硬边界”，材料召回不能变成 runtime 业务关键词白名单。

决策：

- 引入任务内 `MaterialIndex` 和 `MaterialRecallTool`。
- `MaterialIndex` 来自 Ingest 后的 `ParsedDocument`，保存在本次 `GenerationState` 内存中，不进入知识库、不进入向量库。
- 允许以下 Agent 自主提出 `material_queries`：
  - `RequirementAnalyst`：用于需求理解、must include、材料贡献和不确定性判断。
  - `ContentWriter`：用于写作章节、表格、数字、参数、比较和引用证据。
  - `Verifier`：用于核验最终关键 claim 是否有上传材料支撑。
- `Planner` 第一版不直接查询原文，只输出 `evidence_needs`，由 ContentWriter 根据计划和写作需要提出查询。

执行模型：

```text
Agent pass 1
  -> 输出 material_queries
Runtime MaterialRecallTool
  -> 只在本任务 MaterialIndex 中做通用检索
  -> 按 query 数、chunk 数、字符预算裁剪
Agent pass 2
  -> 基于 material_recall_results 输出最终结构化结果
  -> material_queries 清空
```

当前硬边界：

- RequirementAnalyst 最多 3 个 query，约 9000 字 evidence 预算。
- ContentWriter 最多 6 个 query，约 12000 字 evidence 预算。
- Verifier 最多 4 个 query，约 8000 字 evidence 预算。
- 每个 query 返回有限 top chunks。
- Runtime 只做 token overlap、文件名命中、表格/数字/标题等通用结构加权。
- Runtime 不判断业务重要性，不写特定行业词、价格词、车型词或案例词。
- 召回失败不代表材料中不存在该事实；Agent 需要写入 uncertainty / omitted_items / unsupported_claims。

默认 skill / prompt 职责：

- 什么时候该查：
  - 多文件、长材料、表格/数字密集、用户要求精确事实、对比、清单、参数、结论、引用或核验时。
- 怎么写 query：
  - 一个 query 聚焦一个证据目标。
  - 可包含实体、字段、单位、表头、章节名、文件名。
  - 不写“查全部资料”式宽泛 query。
- 如何使用结果：
  - 用 evidence 支撑最终输出。
  - 未命中时保守表达，不编造。
  - Verifier 只为核验关键 claim 查询，不为文风优化查询。

隐私与持久化：

- `material_recall_results` 只在运行时 state 内使用，不作为完整字段写入 job/run。
- Agent artifact 继续基于解析原文和 recall chunk 做敏感短语脱敏。
- 工作流 UI 后续如展示召回，只应展示数量、query 摘要和压缩片段，不能展示完整上传材料。
