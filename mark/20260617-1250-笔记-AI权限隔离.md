# AI 生成链路中的权限隔离

## 一句话概括

AI 生成链路中，模型和 Agent 应负责规划、生成和提出结构化提案，真正的文件写入、元数据更新、构建发布等 Runtime 权限应交给受控服务执行。

## 背景

项目当前已开始建设知识库问答、HTML 生成、上传资料生成、后续 AI 修改和知识库管理等能力。随着 AI 功能从“问答”进入“生成/修改/管理”，系统风险从内容质量问题扩展到执行权限问题。

外部建议指出：标准企业级智能体架构通常会严格区分大模型 API / LangGraph 工作流和 `os.makedirs`、`open/write`、Docker / shell 命令等 Runtime 能力。这一点对项目后续演进有参考价值，但当前不应简单理解为马上重构智能体架构。

## 核心内容

当前评估结论：

- 当前生产 AI 代码中没有发现 Docker、shell、`subprocess` 这类高危 Runtime 命令执行。
- 知识库问答部分已经有较清晰的分层：LangGraph 负责编排，ToolExecutor 按 `allowed_tools` 执行受控工具，API 层负责会话和 run 记录。
- 更需要关注的是生成/修改链路：生成图完成后，同一服务进程会写 HTML、写 metadata、触发 `build_site()`。这不等于失控，但尚未达到企业级“物理隔离”。

推荐的目标边界：

```text
AI Graph / Agent
  -> 只产出结构化 proposal
  -> 不直接拥有任意文件系统或系统命令权限

Policy / Safety Gate
  -> 校验 HTML、metadata、目标路径、分享安全、密钥风险、大小限制
  -> 给出 allow / warn / reject / require_confirmation

Write Gateway / Persistence Service
  -> 根据白名单 capability 执行落盘
  -> 统一处理 create_note、update_note_content、update_metadata、build_site
  -> 负责审计、回滚、重试和错误反馈
```

这类调整本质上属于[[风控收紧]]和[[执行权限治理]]，不是直接提升生成质量的“智能体能力优化”。

> [!tip] 关键要点
> 不要让 AI 直接“写文件”。让 AI 输出可审核的 `proposal`，再由受控 Runtime 服务按白名单能力执行。

> [!warning] 注意事项
> 过早强收紧可能影响生成链路稳定性：模型输出需要符合 schema，安全门禁可能误拦复杂 HTML，失败链路也会变长。因此应先记录原则，等生成/修改质量稳定后逐步落地。

## 实际应用

后续开发建议分阶段推进：

1. 先保留当前生成行为，不立即重构。
2. 在开发文档中记录：生成/修改/知识库管理属于需要 Runtime 权限治理的 AI 板块。
3. 生成链路成熟后，将 `persist_generated_note` 一类落盘能力抽到统一 `WriteGateway`。
4. AI 生成图只返回结构化对象，例如 `CreateNoteProposal`、`UpdateNoteProposal`。
5. `WriteGateway` 负责路径校验、HTML 安全检查、metadata 校验、写入、build 和 run 审计。
6. 若未来接入代码执行、浏览器自动化、PDF 转换、Docker 等能力，必须进入独立 sandbox worker，不能放进主 Web/API 进程。

适用优先级：

- 知识库问答：低优先级，主要是读路径和外部搜索，当前分层基本可接受。
- HTML 生成：中高优先级，涉及新文件写入。
- AI 修改：高优先级，涉及覆盖现有用户内容。
- 知识库管理：高优先级，涉及批量 metadata 改写。
