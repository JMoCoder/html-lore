## 项目概述

本阶段目标是为 HTMlore 的 AI HTML 生成模块完成动手前的完整架构设计。第一阶段业务目标是：用户上传文件并输入需求后，系统通过真实多 Agent 协作生成 HTML 文件，异步写入资料库，默认进入 `inbox` 集合。

本次讨论明确要求吸取知识库问答模块的经验：Runtime 不参与业务判断，避免用硬编码关键词和流程替代智能体决策；HTML 生成作为核心能力，第一阶段优先生成质量、架构正确性和模块解耦，成本优化后置。

## 最终结果

本阶段已形成可执行的 AI HTML 生成总体方案：

```text
受控 Runtime
  -> LangGraph 状态图
      -> Orchestrator / 主控 Agent
          -> 子 Agent 群
          -> Tool Executor / 工具执行器
          -> Skill Loader / 技能加载器
      -> Finalizer / 交付封装器
  -> Write Gateway / 受控写入层
```

已确认的核心设计：

- 主架构采用 LangGraph。
- 第一版所有 Agent 节点统一使用 `gpt-5.5`。
- Runtime 只做硬控制，不做业务判断。
- 主控 Agent 负责语义调度、回退、收敛和最终裁决。
- 子 Agent 负责专业产出：需求分析、规划、写作、样式、HTML 编码、验证、安全审查。
- 文档解析第一阶段采用 `MarkItDown + 本地轻量解析`。
- `tools / 工具` 与 `skill / 技能` 术语已拉平：
  - tools：可执行能力、脚本、外部 API、解析器、安全扫描器。
  - skill：Markdown 驱动的大模型方法包，按需披露、按需加载。
- Agent 不直接写文件，只输出 `CreateNoteProposal / 创建笔记提案`。
- `Write Gateway / 受控写入层` 是 AI 产物进入资料库前的最后工程边界。

## 做得好的地方

1. **及时纠正了问答模块的经验教训**

   这次明确禁止 Runtime 参与业务判断，避免再次出现“代码规则替代 Agent 判断”的问题。业务判断交给 Agent，Runtime 只执行硬规则，这是后续生成质量能否稳定的关键。

2. **架构分层较清晰**

   当前方案明确分出 Runtime、LangGraph、Orchestrator、子 Agent、tools、skill、Write Gateway。每层职责有边界，后续实现、测试、替换和迁移都有抓手。

3. **结构化中间产物设计正确**

   不是让大模型输出一坨自然语言，而是每个节点输出 schema。这符合 LangGraph 的状态图理念，也为回退、验证、前端状态展示、调试和长期演进提供基础。

4. **保留了生成质量优先的空间**

   第一版统一 `gpt-5.5`，允许 Planner、Verifier、Safety Reviewer 等关键节点使用充分模型能力。成本优化后置是合理选择。

5. **安全边界提前进入主设计**

   Write Gateway、Safety Reviewer、HTML 安全扫描、文件权限、解析工具 I/O 权限、开源 license 审查都已进入方案，避免后续临时补安全。

6. **产品可观测性提前考虑**

   异步任务、阶段状态、生成历史、任务详情、阶段 trace 已预留，不会只剩“排队中/完成”这种粗粒度体验。

## 可以改进的地方

1. **文档中仍有部分历史术语需要实现前统一清理**

   架构记录早期使用了 `Skill Executor`、`Tool Skill`、`Workflow Skill` 等说法，后面已修正为 `tools` 和 `skill`。实现前应以本报告为准，代码命名建议统一使用：

   ```text
   Tool Executor / 工具执行器
   Skill Loader / 技能加载器
   tools / 可执行工具
   skill / Markdown 方法包
   ```

2. **状态落库方案还停留在抽象层**

   已确认 `GenerationJob`、`GenerationRun`、`GenerationState` 和 `GenerationStore`，但尚未决定本地 JSON 的具体文件布局、并发锁、失败恢复、schema version。进入实现前需要落成技术设计。

3. **Write Gateway 的事务边界需要谨慎实现**

   “临时文件 -> metadata -> build -> 原子提交”是理想方案，但当前项目文件系统和 build 流程是否支持真正原子提交需要确认。最低标准是不留下半成品。

4. **skill 加载机制需要防止上下文污染**

   skill 是加分项，但如果默认加载过多 Markdown 方法包，会污染上下文并降低稳定性。第一版只应给关键 Agent 加少量基础 skill。

5. **样式增强工具不能压过大模型自主设计**

   方案已确认大模型自主设计是默认路径。后续接入开源设计项目时，要避免模板化、版权风险、品牌风险和外链风险。

## 业务逻辑一致性复查

整体业务逻辑是清晰的：

```text
用户提交文件和需求
  -> 创建异步任务
  -> Ingest 基础解析
  -> Requirement Analyst 形成需求简报
  -> Planner 形成方案和执行清单
  -> Content Writer 写内容草稿
  -> Style Designer 生成样式简报
  -> HTML Coder 生成 HTML 草稿
  -> Verifier 验证需求达成
  -> Safety Reviewer 安全审查
  -> Orchestrator 最终裁决
  -> Finalizer 封装创建笔记提案
  -> Write Gateway 落库到 inbox
```

当前未发现根本性业务冲突。几个已识别并解决的潜在冲突：

- **Final Reviewer 是否独立存在**：已取消固定 Final Reviewer，最终裁决交给主控 Agent。
- **文档解析是否是 skill**：已明确基础解析是 Ingest 固定节点，后续补充能力才通过 tools 按需执行。
- **skill 概念混乱**：已拉平为 tools 与 skill。
- **样式设计是否依赖开源项目**：已明确大模型自主设计是默认路径，开源项目和 skill 是增强项。

## 架构解耦复查

当前解耦程度较好：

- Agent 与工具解耦：Agent 提需求，Tool Executor 执行 tools。
- Agent 与文件系统解耦：Agent 输出 proposal，Write Gateway 写入。
- Prompt/skill 与代码解耦：Agent prompt、Markdown skill、tools 分目录管理。
- 生成状态与前端展示解耦：GenerationStore 提供状态，前端只读 job/run/stage trace。
- 新旧生成图解耦：新增 `generation_v2`，legacy 保留 fallback。

仍需实现时注意：

- 不要让 Agent 代码直接读写文件。
- 不要让 prompt 文件掺入工具执行逻辑。
- 不要让前端依赖 LangGraph 内部字段。
- 不要让 Store 直接绑定本地 JSON 细节，保留 SQLite / Supabase 迁移空间。

## 程序鲁棒性复查

已具备鲁棒性设计基础：

- 异步任务队列和生成历史。
- 阶段状态和 stage trace。
- execution checklist 逐项推进。
- ValidationReport / SafetyReport 结构化回退。
- 最大循环次数和同节点重试上限。
- Safety high-risk hard stop。
- Write Gateway 回滚策略。
- legacy fallback。

实现时需要重点补齐：

- 任务并发控制和单用户生成排队。
- 进程重启后的 pending/running 任务恢复策略。
- JSON store 文件锁或事务写入。
- 大文件解析超时和内存上限。
- LLM 调用失败、超时、半截输出、schema 解析失败的重试策略。
- stage trace 隐私过滤，避免暴露 prompt 或用户敏感原文。

## 高风险敞口

1. **解析工具 I/O 权限风险**

   MarkItDown 和后续解析工具必须只处理受控临时目录文件，禁止任意路径、任意 URL 和不受控网络访问。

2. **HTML 安全风险**

   生成 HTML 可能包含 script、iframe、form、外链、tracking、超大内联资源。必须由 Safety Reviewer + Write Gateway 双层拦截。

3. **开源 license 风险**

   开源设计项目、模板、组件、素材都需要 license 审查。不能把不兼容许可的产物或代码带入生成链路。

4. **Agent 过度自由导致不可复现**

   必须坚持结构化 schema、execution checklist、stage trace，否则多 Agent 会变成不可调试的自由对话。

5. **状态持久化不严谨导致脏数据**

   异步生成如果中途失败，不能留下半成品 HTML、孤立 metadata、错误 manifest 或失效 job 状态。

6. **skill 过载导致上下文污染**

   Markdown skill 应按需加载，第一版少量使用。不要一开始加载一堆“方法包”稀释主任务。

## 经验教训

1. **核心 AI 能力必须先定边界，再写代码**

   问答模块暴露的问题说明：先写 runtime 规则，再补 Agent，很容易把业务逻辑硬编码进系统。生成模块必须反过来，先定 Agent、schema、状态和回退。

2. **多 Agent 不是角色扮演，而是结构化状态协作**

   真正可工程化的多 Agent 需要独立职责、独立输入输出、可回退状态和可审计 trace。

3. **Runtime 不是敌人，但必须收敛到硬控制**

   Runtime 应该强在状态、权限、重试、并发、写入、安全硬规则；弱在业务判断和内容决策。

4. **Write Gateway 是生成与修改模块的共同底座**

   生成 HTML、修改现有笔记、知识库管理都需要受控写入层。这里做好，后续 AI 修改会少很多风险。

5. **tools 与 skill 必须分开**

   tools 是可执行能力，skill 是大模型方法包。混用会导致权限边界、加载策略和代码结构混乱。

## 可复用的模式 / 工具 / 方法

- `GenerationState / 生成状态`：统一承载所有中间产物。
- `execution_checklist / 执行清单`：Planner 定义完成标准，后续节点逐项更新。
- `ValidationReport.route_back_to`：让回退基于结构化字段，而不是 Runtime 关键词。
- `SafetyReport + Write Gateway`：AI 内容进入资料库前的双重门禁。
- `Skill Loader + Tool Executor`：区分方法包和执行工具。
- `generation_v2 + legacy fallback`：大型 AI 架构重构的安全迁移方式。
- `stage_trace`：同时服务前端状态页、调试、审计和未来过程回放。

## 完整需求报告

### 一、第一阶段目标

用户上传文件并输入需求后，系统通过多 Agent 协作生成 HTML 文件，异步写入资料库，默认进入 `inbox` 集合，并可在生成历史/任务队列中查看状态。

### 二、第一阶段支持范围

输入文件：

- HTML
- Markdown
- TXT
- PDF
- Word
- PPT

暂不做：

- Excel
- 链接生成
- OCR
- 复杂网页抓取
- 高级 PDF/PPT 专业解析
- 开源设计项目正式接入
- 复杂过程回放 UI

### 三、核心流程

```text
Create Generation Job
  -> Ingest / Parser
  -> Requirement Analyst
  -> Planner + Execution Checklist
  -> Content Writer
  -> Style Designer
  -> HTML Coder
  -> Verifier
  -> Safety Reviewer
  -> Orchestrator Final Decision
  -> Finalizer
  -> Write Gateway
  -> inbox
```

### 四、核心数据结构

- `ParsedDocument / 解析后的文档`
- `RequirementBrief / 需求简报`
- `PlanDraft / 方案草案`
- `ExecutionChecklist / 执行清单`
- `ContentDraft / 内容草稿`
- `StyleBrief / 样式简报`
- `HtmlDraft / HTML 草稿`
- `ValidationReport / 需求验证报告`
- `SafetyReport / 安全审查报告`
- `CreateNoteProposal / 创建笔记提案`

### 五、模型策略

- 第一版统一 `gpt-5.5`。
- 保留 `GenerationModelProfile`，后续支持按节点配置模型、失败升模型、低风险节点降模型。

### 六、文件组织建议

```text
html_lore/server/ai/generation_v2/
  graph.py
  state.py
  schemas.py
  orchestrator.py
  agents/
  prompts/
  skills/
  tools/
  write_gateway.py
  model_profile.py
```

### 七、前端最小需求

- 复用生成历史/队列入口。
- 显示任务标题、状态、阶段、创建/完成时间、错误摘要、打开结果、重试。
- 详情页第一版只展示 stage trace。
- 不展示完整模型思考和内部 prompt。

### 八、落库要求

- 默认 collection = `inbox`。
- source_type = `ai_generated`。
- Write Gateway 负责路径、文件名、metadata、HTML 安全、build 和回滚。

### 九、测试验收

第一版交付至少满足：

- Markdown / HTML / PDF 跑通。
- 有样式参考的生成结果能体现风格影响。
- 安全失败样例能被阻断。
- 异步状态可见。
- 成功生成后进入资料库 `inbox`。
- legacy 生成路径可 fallback。
