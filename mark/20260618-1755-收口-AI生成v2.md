## 需求背景

今天进入 AI 生成模块第一阶段开发，目标是先搭建“用户上传文件 + 需求 + 可选样式文件 -> 生成 HTML 笔记 -> 默认入库 inbox”的 v2 生成链路。

该模块是后续“基于问答生成笔记、上传文件生成 HTML、修改现有笔记、知识库管理”的核心底座，因此要求采用可复用的 LangGraph/多 Agent 工作流，Runtime 只负责状态、边界、安全与熔断，不参与内容业务判断。

## 解决方案

本阶段采用 `HTML_LORE_AI_GENERATION_ENGINE=v2` 显式开启新链路，默认仍保留 legacy 生成作为稳定降级路径。

v2 链路按以下 Agent/节点组织：

- `Ingest / Parser`：解析用户上传材料与可选样式参考文件。
- `RequirementAnalyst`：理解用户需求、目标、受众和约束。
- `Planner`：产出页面结构、内容策略、视觉策略、检查清单。
- `ContentWriter`：基于材料和计划生成结构化内容草稿。
- `StyleDesigner`：生成样式 brief，支持默认设计、约束设计、参考文件设计。
- `HTMLCoder`：生成自包含静态 HTML。
- `Verifier`：验收需求达成度，必要时路由回前置节点修订。
- `SafetyReviewer`：做模型层安全审查。
- `Finalizer`：包装为可写入资料库的 note proposal。
- `WriteGateway`：Runtime 硬安全扫描并写入内容目录，重建 manifest。

外部模型调用统一走 `ProviderGenerationModelClient.complete_json()`，每个 Agent 都要求返回结构化 JSON。模型选择仍保持显式配置，第一版使用已确认的 `gpt-5.5`，不在代码里擅自切换模型。

## 遇到的问题

1. 真实 smoke 初次运行长时间无输出。

原因是临时脚本 stdout 缓冲，且 v2 多 Agent 串行调用耗时较长。随后改成无缓冲脚本并包装模型客户端，输出 `NODE_START / NODE_DONE`，定位到具体 Agent。

2. 发现旧验收报告导致 `HTMLCoder` 重复执行。

`Verifier` 判定不通过后路由回 `HTMLCoder`，但 `HTMLCoder` 生成新 HTML 后没有清空旧的失败 `validation_report`，编排器继续读取旧失败结论，导致重复进入 `HTMLCoder`。已修复。

3. 修复状态后，流程变成正常的 `HTMLCoder -> Verifier -> HTMLCoder -> Verifier`，但仍不收敛。

这说明已经不是单纯 Runtime 状态 bug，而是质量验收策略和修订反馈链路需要继续优化。已加入 `max_revision_rounds` 熔断，避免无限消耗。

4. 真实 smoke 最后一次为了检查 Verifier 具体不通过原因，启动了 `/tmp/html_lore_v2_inspect_verifier.py`，但用户要求今天到此为止，已中断，未获得 Verifier 结构化原因日志。

## 值得注意

- 这次真实 smoke 证明“Runtime 状态控制”非常必要：没有熔断和阶段日志，多 Agent 真实调用会很容易变成长时间无反馈和成本不可控。
- Runtime 可以做状态清理、最大步数、最大修订轮次、安全扫描和写入边界；但不应替 Agent 判断内容业务质量。
- `Verifier` 是下一阶段最关键风险点。它如果过严，会导致永远无法交付；如果过松，会降低生成质量。后续应把它定位为“严重问题拦截 + 小问题警告”，而不是无限追求完美。
- `HTMLCoder` 修订路径要确认是否有效消费上一轮验收意见，否则多 Agent 只是形式上协作，实际不会收敛。
- 当前 v2 真实调用耗时较长，后续业务稳定后需要考虑：
  - 并行化可并行节点；
  - 减少不必要 Agent 调用；
  - 针对简单任务走轻量路径；
  - 将 debug trace 和成本统计纳入任务详情。
